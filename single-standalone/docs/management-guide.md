# Management guide

Task by task. Each section says when to use an area, shows one worked example with the exact command and what it prints, and lists what the command refuses and why. Every flag and exit code is in [reference.md](reference.md).

Output lines start with `[mcctl]` on stderr. A refusal prints `[mcctl] ERROR:` and exits with 2 (usage), 3 (configuration), or 4 (refused for safety). Placeholders such as `<archive>` stand for values the command fills in.

## Worlds

Use this to back up, replace, make, or move a world. A world is `data/WORLD` with its `WORLD_nether` and `WORLD_the_end` beside it; these three move together.

```
mcctl world survival backup
[mcctl] survival: world saved to <archive> (verified with tar -tzf)

mcctl world survival restore world <archive>
[mcctl] survival: world restored from <archive>
```

`backup` works on a running server: the server saves and pauses writes around the archive. `restore` needs a stopped server:

```
mcctl world survival restore world <archive>
[mcctl] ERROR: survival is running: stop it first (mcctl stop survival). World changes need a stopped server; nothing was changed
```

What this refuses and why:

- Restore, delete, reset, or import on a running server. A world written during the change can be copied or replaced only partly.
- Deleting the active world. `delete` refuses it; `reset` does not, because the server makes a new one at its next start.
- An archive whose top level holds anything other than the world and its nether and end. A restore names the top-level folder it found and changes nothing.
- A world name that is not a plain name.
- Any restore or delete when the copy of the current world into `safety/` cannot be verified. Nothing is removed in that case.

## Settings and drift

Use this to change `server.env` values (view distance, MOTD, difficulty and so on). A change is written to disk first; the running container picks it up at `apply`. `mcctl status NAME` says which one is current.

```
mcctl set survival VIEW_DISTANCE=12
[mcctl] survival: config pending: mcctl apply survival

mcctl status survival
...
config:    pending (mcctl apply survival)

mcctl apply survival
[mcctl] survival: applied (recreated, still stopped)
```

If the server is running, `apply` restarts it. With players online it refuses unless you pass `--yes`:

```
mcctl apply survival
[mcctl] survival: 2 players online
[mcctl] ERROR: survival has 2 players online; pass --yes to restart it and apply the change
```

What this refuses and why:

- A key that is not a known setting, unless `--force`. The message names the key: `FOO is not a known setting`.
- A credential (the RCON password, the CurseForge key). It is a file under `secrets/` and is refused even with `--force`. No output of these commands shows its value.
- A structural key (`MEMORY`, `CPUS`): `set` refuses, and points to `mcctl edit` (`AUTOSTART` goes through `mcctl autostart`). The compose file must be regenerated by the command that owns the limit.
- A reserved key (`RCON_PORT`, `ENABLE_RCON`, `RCON_PASSWORD_FILE`, `CF_API_KEY_FILE`): `mcctl`'s RCON and CurseForge wiring depends on them.
- A value that does not fit its type: the message says what was expected (for example, a whole number of at most 9 digits).
- `apply` on a running server with players online, without `--yes`. A "no" at the confirm changes nothing.
- A refused `set` leaves `server.env` as it was, byte for byte.

## Files

Use this to look at, copy, or edit what is under a server's `data/` without a shell in the container. The commands run in a helper container, so they work the same whether the server runs or not.

```
mcctl files survival ls world/datapacks
```

This prints one name per line. The usage line lists the verbs: `ls`, `cat`, `get`, `put SRC PATH [--force]`, `rm PATH [--recursive]`, `mkdir`, `mv SRC DEST`, `edit`.

What this refuses and why:

- A path outside the server's `data/`: an absolute path, a `..` component, or a symlink that leads out. The rule is that a path can never reach the secrets, the compose file, or another server.
- A name that starts with `-` is passed as a path, never as an option (`-rf` is sent as `./-rf`).
- `rm` of a folder without `--recursive`: `is a folder: add --recursive to remove it and everything in it`, exit 4.
- An overwrite by `put` without `--force`: `already exists in the data of NAME: refused (add --force to replace it)`, exit 4. A folder is never replaced by `put`.

## Players

Use this for the whitelist, operators, and bans. These commands talk to the running server over RCON, so the server must be running.

```
mcctl whitelist list survival
There are no whitelisted players
```

The server's own reply is printed as it is. `whitelist list --names` prints the player names; `whitelist import SERVER FILE` takes a text file with one name per line.

What this refuses and why:

- An IP address that is not IPv4 or IPv6 (`ban-ip`, `pardon-ip`): the address is checked before anything is sent.
- An import file with more than 500 names. Split it; the server takes a batch at a time.
- `--persist` on a stopped server. It is refused before anything is stored, because there is no running server to apply it to.
- Any command that would print the RCON password. Output and calls are checked to hold none of it.

## Mods, plugins and Modrinth

Use this to keep the server's mod or plugin list. `mcctl mods` keeps a list for mods, `mcctl plugins` for plugins, and `mcctl modrinth` takes Modrinth projects. An entry is an `https://` URL, a file in the server's `mods/` folder, or a Modrinth slug. The list is written to `lists/`; `sync` makes the container match it.

```
mcctl mods survival add https://example.com/mods/tool.jar
[mcctl] config pending: mcctl mods survival sync
```

What this refuses and why:

- An entry that is not a file, not an `https://` URL without credentials, and not a container path under `/mods/` or `/plugins/` without `..`. The whole `add` is refused and nothing is changed: `nothing was changed`.
- A Modrinth entry with characters outside letters, digits, `.`, `_` and `-`: `is not a Modrinth project`.
- A list that is refused in full. No file is copied and no list is written for a batch that has one bad entry.

## Versions and loaders

Use this to see or change the Minecraft version, the server type, and the loader version. A version change takes a verified safety archive of the world first.

```
mcctl version survival show
VERSION: 1.21.1
TYPE: PAPER
```

If no version is set, `show` prints `VERSION: (not set: the image uses LATEST)`.

```
mcctl upgrade survival --to 1.20.4
[mcctl] ERROR: refused: 1.20.4 is older than 1.21.1. A world saved by a newer version can be damaged by an older one; pass --allow-downgrade to change it anyway
```

What this refuses and why:

- A downgrade, unless `--allow-downgrade`. A world saved by a newer version can be damaged by an older one. This is exit 4.
- `--loader-version` for a type that has no loader variable (for example PAPER): exit 2.
- `reinstall` for a type that has no reinstall flag: exit 2.
- A change from Forge to Fabric while two jars sit in `mods/`: refused, exit 4, because the jars cannot be told apart.
- A change to LATEST that asks for confirmation when there is no terminal and no `--yes`: refused, exit 4.
- A change on a running server whose container is not healthy after the wait: the command says so.

## Modpacks

Use this for a server whose content comes from a CurseForge or Modrinth pack. The pack is itzg's built-in support, so `mcctl` only writes the variables and recreates the container.

```
mcctl modpack survival info
no modpack
```

For a server with a pack, `info` prints the resolved name and version. A stopped container cannot report them, so `info` prints `unknown` for them.

What this refuses and why:

- `--clean` on a stopped server, exit 4. The clean install has to run in a running container. The message says so and changes nothing.
- `--purge-mods` on a running server, exit 4: it changes the mods of a stopped server only.
- A CurseForge pack without `secrets/curseforge_api_key`, exit 3. Nothing else runs first.
- `CF_API_KEY_FILE` in a server's `modpack.env`, exit 3: `mcctl` owns that key.
- `update` on a server with no modpack, exit 1.

## Clone, rename, export and import

Use these to copy a server to a new name, to rename one, or to move one to another host as an archive. A clone is made stopped; start it when you are ready.

```
mcctl clone survival survival-test
[mcctl] cloned survival to survival-test (stopped). Start it with: mcctl start survival-test; players join at survival-test.mc.example.net

mcctl export survival survival.tar.gz
[mcctl] exported survival to survival.tar.gz

mcctl import survival.tar.gz survival-copy
[mcctl] imported survival.tar.gz as survival-copy (stopped). Start it with: mcctl start survival-copy; players join at survival-copy.mc.example.net
```

`export` holds no secrets unless you pass `--with-secrets`; the archive's `mcctl-export` marker says `secrets=0`. `import` needs that marker.

What this refuses and why:

- `clone` of a running server without `--yes`: `pass --yes to copy a running server`, exit 4. A running server's files can change during the copy.
- `import` of an archive without the `mcctl-export` marker: `it is not an export of mcctl: nothing was imported`, exit 4.
- `import` of an archive with a member name that is absolute, has `..`, or is a link. The check runs before anything is extracted, and nothing is written outside the target.
- A new name whose DNS record cannot be made: nothing is kept, exit 1.
- A new name that a leftover folder or a leftover container already uses: `a leftover of an interrupted create or delete`, exit 4. Clean that up first.
- `export --with-secrets` when `secrets/rcon-NAME` is missing: nothing is exported, exit 1.
